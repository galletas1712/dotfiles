# Shared development container

The host keeps the container engine, chezmoi, shell tools, `gh`, `jq`, `zmx`, and host copies of Codex and Claude Code. This image provides Linux copies of Codex, Claude Code, Pi and Cursor Agent; the shared Kubernetes clients `tsh`, `kubectl`, `helm`, `k9s` and `vcluster`; and Node LTS with `npm`/`npx`, `uv`, and a Go starting toolchain. `kind`, `minikube`, `kubebuilder` and `kubelogin` are absent. Project dependencies and any additional language runtimes belong in each project's own files or image.

| Work | Shared image | Per project |
| --- | --- | --- |
| Python | `uv` executable; no chosen development Python | `.python-version` and `pyproject.toml` choose Python; `uv.lock` and `.venv` hold that project's dependencies. `uv sync` downloads the requested interpreter if needed. Interpreters are cached by version in the container home, rather than copied into every project. |
| JavaScript/TypeScript | Node LTS, `npm` and `npx` for the agents and ordinary projects | `package.json`, `package-lock.json`, local `node_modules` and a local `typescript` dev dependency. Use `npm ci` and project scripts such as `npm run typecheck`; do not install TypeScript globally. A project needing another Node major version uses its own image. |
| Go | Current `go` command as a starting toolchain | `go.mod`/`go.sum` record modules and Go requirements; Go can download a newer toolchain when a module requests one. A project requiring an exact older toolchain uses its own image. Keep Go tools as module tool dependencies where supported. |

The shared image follows current releases on rebuild. Project locks and runtime requirements stay stable until the project deliberately updates them. This lets the common shell upgrade without silently changing application dependencies. C/C++ compilers and headers are added in projects that need native builds. Ignore project `.venv` and `node_modules` directories in Git, and recreate them separately on Mac's Linux ARM guest and Odin's Linux x86 guest. [uv Python versions](https://docs.astral.sh/uv/concepts/python-versions/), [uv projects](https://docs.astral.sh/uv/guides/projects/), [npm clean install](https://docs.npmjs.com/cli/commands/npm-ci/), [TypeScript project install](https://www.typescriptlang.org/download/), [Go toolchains](https://go.dev/doc/toolchain)

Run `bash dev-shell.sh` to start in host `~/workspace`, which appears as `/home/<username>` in the container. Pass `/absolute/path/to/project` to start in another project. Then start `codex`, `claude`, `pi`, or `cursor-agent` in that shell. Add `-- command` after the path to start an agent directly. Run `bash dev-shell.sh --docker /absolute/path/to/project` when the session must build or run sibling containers. The launcher uses host networking, so host and container services can reach each other on `localhost` without publishing ports. The launcher checks base images on every start and refreshes packages once a day when used; other starts use the build cache. It does not start a second Docker daemon.

Use `--mount-host /absolute/path` before the project path to expose an additional host file or directory at the same path inside the container. For a path directly under the host home, the launcher also exposes it under `/home/<username>` so a symlink from host `~/workspace` into the parent home works in the container. Repeat the option for separate paths. These mounts are chosen on each host and are not part of the shared dotfiles.

Projects inside host `~/workspace` appear directly under `/home/<username>` in the container. A selected project outside `~/workspace` is bind-mounted at its host absolute path, so edits are visible on the host and sibling Docker bind mounts can use that path. This is a local share on each machine; Git remains the way to move work between Mac and Odin.

The launcher creates host `~/workspace` if needed and mounts it as `/home/<username>`, the container user's home. It creates an account with the host's username and numeric user/group IDs at startup, then drops root privileges. That account has passwordless `sudo` for container administration. Existing host `.tsh`, `.kube`, `.codex`, `.claude`, `.pi`, `.cursor`, `.agents`, `.docker`, `.azure`, `.aws`, `.ngc`, `.config/gh`, `.config/cursor`, `.config/gcloud`, `.config/az` and `.config/ngc` state directories are mounted **read-write** under the container home; when the host home has a different absolute path, they are also mounted there. This shares Kubernetes, registry, cloud CLI, and agent state without mounting the entire host home. Codex, Claude, Pi and Cursor use their original host configuration paths, so saved sessions and absolute references remain valid. The host `.claude.json` file is mounted at both paths when needed. On macOS, Cursor desktop's separate `Library/Application Support/Cursor/User/History` directory is exposed read-only at `~/.config/Cursor/User/History` in the container.

On Odin, `~/.docker/config.json` contains Docker registry logins for NVCR, ACR and ECR, so the container's Docker client reads those from the shared directory. On macOS, Docker's `osxkeychain` credential helper cannot run inside the Linux container; sharing the config file alone does not share those keychain secrets. Sign in separately from the container if a registry needs authentication there. Azure, AWS and Google Cloud credentials are shared when their host directories exist, but their CLIs are not installed by this image solely for that reason. A custom credential path can be passed with `--mount-host`.

The launcher does not call `tsh` or require a host Teleport login to build. The image installs Teleport from its official `stable/rolling` APT channel, and an existing host `~/.tsh` directory is mounted for use at runtime. Log in on the host before using Teleport inside the container. Teleport does not support clients from a newer major version than the cluster, so check actual cluster access after a major release. Host Teleport and Kubernetes configuration with absolute paths still needs a workflow check. GitHub CLI comes from its official signed APT repository; there is no GitHub-maintained one-line install script. `kubectl`, Helm 4, K9s and vCluster follow current releases. A `kubectl` client is supported only within one minor version of the cluster API server, so use a cluster-compatible client if a Teleport cluster lags behind. Check Helm 4 against the actual vCluster workflow before relying on it for cluster changes; vCluster's published prerequisites still mention Helm 3.10. Cursor Agent is installed into the Linux image during each refresh so the Mac host's executable is never run inside the guest. [Kubernetes version skew](https://kubernetes.io/releases/version-skew-policy/), [Helm installation](https://docs.helm.sh/docs/intro/install/), [K9s installation](https://github.com/derailed/k9s#installation), [vCluster CLI](https://www.vcluster.com/docs/vcluster/manage/sleep-wakeup#prerequisites)

The launcher carries the host Git name and email into the container and configures `gh` as its HTTPS credential helper when shared GitHub CLI state exists. Commit signing inside the container needs a separate setup.

The `--docker` mode mounts the host Docker socket. Any process in that session can control the host's Docker engine, including creating containers with other host mounts. Use it for trusted build work only. On Mac, start OrbStack first.

The image with the Kubernetes and language tools built on Mac ARM through OrbStack and on Odin x86_64. Node/npm/npx, uv, Go, kubectl, Helm, K9s, vCluster, and the agent CLIs started on both architectures. On both hosts, the launcher created the `schwinns` account with the host UID/GID, mounted host `~/workspace` as home, and verified passwordless sudo and the host Docker connection. Mac tests also verified home writes, agent history mounts, `tsh kube ls` with the shared login, host networking to a Mac `localhost` service, and a small sibling Docker build. Odin's sibling Docker build also worked. A later read-only `kubectl` query prompted for fresh browser authentication, so cluster compatibility remains unverified. Agent conversation resume and commit signing still need workflow checks.

The launcher refuses a Linux build when either the workspace or Docker filesystem has less than 20 GiB free; that is a startup check, not a limit on files written during a session. Daily refreshes can accumulate Docker build cache over time; the launcher does not run a global Docker prune, which could remove unrelated caches or images.
